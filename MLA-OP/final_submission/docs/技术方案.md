# DeepSeek MLA Decode 内核技术方案

本方案针对揭榜挂帅 XH-202608 赛题「DeepSeek MLA Decode」，在沐曦 MetaX C500 上用 TileLang 实现单文件算子内核。最终成绩为 OJ 平台 98.17 分（589/6），排名第 1，领先第二名 0.34 分。

## 1. 题目与目标

### 1.1 计算语义

输入为 query、query 的 RoPE 部分、KV cache 与 KV 的 RoPE 部分，形状固定为 batch=1、heads=16、kv_heads=1、dim=512、pe_dim=64，kv_ctx 取 2048 到 65536 六档。计算为标准的 MLA Decode 单步注意力：

```text
score = q @ kv^T + q_pe @ k_pe^T
out   = softmax(score * (dim + pe_dim) ^ -0.5) @ kv
```

这是 decode 阶段，每个 query 只有 16 行（16 个 head），却要对整个 KV cache 做注意力。因此算子天然是访存主导、且并行度极低——整个问题只有 16 行输出。

### 1.2 计分规则

判题机对每个 case 报告内核耗时 `k`（毫秒，三位小数，即微秒级量化），按官方基线耗时折算：

```text
ratio   = base / (base + k)
display = floor(100 * ratio)
```

总分是 6 个 case 的 `display` 整数均值。因为 `k` 先量化再参与计算，相邻两档往往只差 1 微秒，例如 2048 档的 96 分需要 `k ≤ 0.01296`，而 `k = 0.013` 给出 96.99%、`k = 0.012` 给出 97.22%，只差 0.01 个百分点。

### 1.3 起点与终点

| case | 基线 / ms | 起点 k | 起点 display | 终点 k | 终点 display |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2048 | 0.419 | 0.017 | 96 | 0.012 | 97 |
| 4096 | 0.789 | 0.021 | 97 | 0.016 | 98 |
| 8192 | 1.526 | 0.031 | 98 | 0.023 | 98 |
| 16384 | 3.000 | 0.051 | 98 | 0.031 | 98 |
| 32768 | 5.958 | 0.091 | 98 | 0.050 | 99 |
| 65536 | 11.840 | 0.170 | 98 | 0.088 | 99 |

总分从 97.17 提升到 98.17，排名从第 3 升到第 1。

## 2. Kernel 设计方案

### 2.1 总体结构

整个算子是一个 TileLang 单文件模块，对外只暴露一个函数：

```python
run_kernel(q, q_pe, kv, k_pe, output, batch, heads, kv_heads, kv_ctx, dim, pe_dim)
```

模块内部按 shape 特化编译。每个 `kv_ctx` 对应一份独立的 kernel，编译在首次调用时由 `tilelang.jit` 自动完成并缓存。

主 kernel 采用 split-KV：把 KV cache 按 key 切成 `num_split` 段，每段由一个 CTA 负责，最后再用一个融合的归并阶段把各段的局部注意力结果按 LSE 归一化后相加。这样把一个「只有 16 行输出」的问题，变成 64 到 104 个 CTA 并行的问题。

### 2.2 单块内的线程与内存布局

每个 CTA 处理 32 个 key（`block_n = 32`）与全部 16 个 head。共享内存布局如下：

| 缓冲 | 形状 | 字节 | 用途 |
| --- | --- | ---: | --- |
| `Q_shared` | [16, 512] fp16 | 16384 | QK 的 A 操作数 |
| `Q_pe_shared` | [16, 64] fp16 | 2048 | PE 项 A 操作数 |
| `KV_shared` | [32, 512] fp16 | 32768 | QK 的 B 操作数与 PV 的 B 操作数 |
| `K_pe_shared` | [32, 64] fp16 | 4096 | PE 项 B 操作数 |
| `S_shared` | [16, 32] fp16 | 1024 | softmax 结果，QK 与 PV 的交接面 |
| `O_shared` | [16, 512] fp16 | 16384 | 输出转置暂存，与 Q 区别名 |

循环体的峰值是 56576 B，低于每 SM 的 65536 B 上限。

线程划分是关键决策。QK 乘法的形状是 M16 × N32，只能分成 1 × 2 的 warp 划分，即 2 个 warp；而 PV 乘法的形状是 M16 × N512，可以分成 1 × 4 甚至 1 × 8。因此 QK 放在 `T.ws(0)` 内执行，由 layout inference 把 `thread_bounds` 收窄到 128 线程；PV 放在 `T.ws` 之外，让全部线程参与。

注意本机 warp 宽度是 64，不是常见 GPU 的 32。这一点直接影响所有「多少 warp 在干活」的判断。

### 2.3 融合归并

split-KV 的代价是归并。常见做法是再启动一个 kernel，但这里采用**单 kernel 内的软件到达屏障**：

1. 每个 CTA 把自己的局部结果写入全局 `output_partial`，并把局部 LSE 写入 `glse`。
2. 各 CTA 用 `atomic_add` 递增一个全局计数器，然后自旋等待计数器达到本轮的目标值。
3. 到达后，前 64 个 CTA 各自负责一个 (head, 列块)，把 `num_split` 份局部结果按 LSE 权重相加，直接写出最终结果。

这样做省掉了第二次 kernel 启动，也省掉了中间的显式同步。计数器的目标值按「每次启动增加 `num_split`」的方式推算，因此计数器必须**按 shape 各存一份**——否则同一进程先后跑 64 split 与 104 split 时会永久自旋。这个问题在早期版本中真实存在，已修正。

### 2.4 路径分派

内核按 shape 是否特化出多条路径，全部在编译期决定，运行期没有分支开销：

| 条件 | 路径 | 说明 |
| --- | --- | --- |
| `num_split == 1` | `main_no_split` | 短上下文退化路径 |
| `seqlen_kv < 4096` | `main_split` | 每 CTA 一个 tile，512 线程 |
| `seqlen_kv >= 4096` | `main_split_pref` | 3 barrier / tile，预取拆两组，512 线程 |

长路径额外把下一个 tile 的 KV 预取拆成两组，分别落在两个 barrier 区间里；短路径因为只有一个 tile，预取无处可藏，改为把 512 线程全部用于加速转储与归并。

## 3. 技术路线

### 3.1 先建性能模型，再谈优化

优化初期最大的浪费来自「凭直觉改、凭感觉判断」。本方案先花时间把成本模型量出来：

```text
time = 固定成本 + 每 tile 成本 × tile 数
```

用「把循环强制写成 0 次 / 1 次」的消融直接测出固定成本，再用 5 / 10 / 20 个 tile 三点定出斜率。测出来的几个关键常数是：

- 空 kernel 的设备时间 2.87 微秒，这是无法消除的启动税
- 单条 16×16×16 fp16 MMA 的吞吐下限约 20.4 纳秒
- 显存带宽强烈依赖传输规模：4 MB 只有 209 GB/s，8 MB 为 358，64 MB 为 1059，256 MB 为 1373
- 每个 SM 只驻留 1 个 CTA，grid 从 104 加到 208 时耗时变成 1.78 倍

最后一条解释了为什么 `num_split` 取 104 而不是更大：超过 SM 数的 CTA 无法共驻，融合归并的到达屏障会死锁。

### 3.2 逐层定位瓶颈

有了模型，就能判断每一档该往哪里打。以 32768 为例，分解为固定 10.5 微秒加 9.85 个 tile；每个 tile 又拆成 MMA（2.79 微秒，已是硬下限）与拷贝（2.2 微秒）两部分。两者当时几乎完全串行，于是方向明确：把拷贝藏进 MMA 窗口。

每档的目标都按同样的方法算：先算出现在 `k` 与下一档门槛的差，再判断这个差是否小于该档可用的物理余量。这一步避免了大量无效工作，例如 2048 档需要再降 3.5 微秒，而启动税就有 2.87 微秒、split 归并往返还有约 3.9 微秒，直接判定该档不可达。

### 3.3 测量方法

本机环境有三个坑，方案里统一规避：

1. `torch.profiler` 在这套 MACA 栈上返回的数据不可信，全部改用 CUDA event 计时。
2. 单次 launch 的事件计时在短 kernel 上是 host-bound 的，会读到 56 到 60 微秒；必须用「连续多次 launch 取平均」的突发计时，或 CUDA graph 重放。
3. 进程间漂移可达 ±0.7 微秒，且固定顺序会让先跑的模块偏慢约 0.4 微秒。因此所有对比都在同一进程内交错进行，并轮换顺序。

所有改动在提交前都必须过数值门：与基线逐元素比对，显式检查 NaN，长上下文单独验证。仅本方案就拦下了三处会静默出错的改动——`ws` 内的 barrier 在 MACA 上是空实现所导致的竞态、寄存器暂存的 WAR 串行化、以及一个已存在的进程内死锁。

## 4. 创新点

### 4.1 split 边界按 tile 对齐

最初的切分公式是 `kv_start = seqlen_kv * bz // num_split`，每个 CTA 的起点会落在任意 key 上。这样 104 个并发流的拷贝效率掉了一半。

改为按 tile 对齐：

```python
tiles_total = seqlen_kv // block_n
kv_start = ((tiles_total * bz) // num_split) * block_n
kv_end   = ((tiles_total * (bz + 1)) // num_split) * block_n
```

改完后 104 split 反而全面优于 64 split（65536 从 0.157 ms 降到 0.111 ms，display 从 98 升到 99）。此前「split 不能超过 64」的结论是被未对齐污染的。

### 4.2 32 键整块寄存器暂存

把循环头的全局到共享拷贝，改成**整块 32 键暂存进寄存器**：LDG 在循环头发车，STS 在 PV 吃完当前 tile 之后落回 `KV_shared`。这样正好塞进已有的那个 barrier，不新增同步、不多占共享内存，寄存器 238 个、零 spill。

实现上有三个必须绕开的坑：

- `mtregisters` 上限是 254，且只通过 `*(uint4*)` 强转访问的局部数组会被降级到栈（148 B 栈帧，耗时从 64 微秒涨到 101 微秒）。解法是强转写、逐元素读。
- TileLang 会给各分块复用同一个向量临时变量，导致所有 LDG 被 WAR 串行化。解法是用独立的 `kv_s0` 到 `kv_s7` 缓冲。
- `T.sync_threads()` 会强制未完成的 LDG 先完成，所以预取的掩护窗口只有「发出点到下一个 barrier」之间。

三处都修好后，32768 从 0.064 降到 0.057，总分 586 变 587。

### 4.3 短上下文的三连击

2048 档只有 1 个 tile，预取无处可藏，瓶颈全在固定成本。三项改动都是逐字节一致的：

- **只在单 tile 路径开 512 线程**：PV 走 8 warp，`O_shared` 的 fp32 到 fp16 转储从 2.6 微秒降到 0.81。寄存器反而从 78 降到 48。
- **归并的 LSE 用 5 次 warp shuffle**：MACA 的 `AllReduce<SumOp,128>` 会做一次无保护的 offset-64 共享内存往返（因为 `__sync_thread_partial` 是空实现），而结果只有 thread 0 使用。降到 0.12 微秒。
- **把 mid-PV barrier 折进已守卫的预取块**：该 barrier 在单 tile 下恒为死代码。

合计让 2048 从 15.93 微秒降到 14.40。

### 4.4 共享内存的 bank conflict

`O_shared` 的行跨度是 512 个 half，即 256 个字，对 32 取模正好为 0。结果是持有 row 0 到 15 同一列组的 16 条 lane 全部命中同一个 bank——**16 路冲突**。这个代价此前一直被误记为「0.81 微秒的转储开销」，实际是 2.74 微秒。

两种修法都验证过：行跨度补到 520 个 half（260 字，模 32 为 4，2 路冲突，且 1040 B 的行仍是 16 B 对齐，全局 store 保持 `uint4` 合并）；或对索引做旋转 skew。`S_shared` 同样处理（8 路降到无冲突）。

注意不能用 XOR swizzle：它会把全局 store 退化成 `uint2`，8 B 存储的惩罚 0.65 微秒大于冲突收益 0.18 微秒。

### 4.5 3 barrier 的 fast path 下放到中段

把 3 barrier、预取拆两组的快速结构从 `seqlen_kv >= 16384` 下放到 `>= 4096`，沿途再加两处 bank skew，得到：

| case | 改动前 | 改动后 |
| --- | ---: | ---: |
| 4096 | 19.70 | 17.22 |
| 8192 | 29.03 | 24.24 |

4096 由此从 97 升到 98，总分 587 变 588，成为独占第一的那一分。

### 4.6 融合归并的单 kernel 实现与 per-shape 计数器

归并在同一 kernel 内用软件到达屏障完成，省掉第二次启动。所有 CTA 发布局部结果后递增全局计数器并自旋，前 64 个 CTA 负责归并。

这里修掉了一个**既有缺陷**：计数器的目标值按 `(fuse_old // num_split + 1) * num_split` 推算，隐含假设每次启动时计数器是 `num_split` 的整数倍。若同一进程先后跑 64 split 与 104 split（例如 2048 与 8192），计数器会永久自旋。改为按 shape 各存一个计数器，零成本、不需要额外的清零操作。

## 5. 实现步骤

内核按版本迭代，每一步都在 OJ 上实测。关键节点如下：

| 版本 | 关键改动 | OJ display | 提交号 |
| --- | --- | ---: | --- |
| `v021` | 自适应 split 策略与 no-max softmax | 97.17 | — |
| `v039` | split 边界按 tile 对齐，`num_split` 提到 104 | 97.67 | 168534 |
| `v042` | 32 键整块寄存器暂存（LDG 提前、STS 延后） | 97.83 | 168733 |
| `v043` | 4096/8192 走 3 barrier fast path，修 O/S 的 bank conflict | 98.00 | 168830 |
| `v044` | 2048 路径补 `O_shared` padding，到达自旋改 volatile load | **98.17** | 168869 |

最终提交件为 `src/mla_decode_submission.py`，与 OJ 提交号 168869 的文件逐字节一致（md5 `23ae084483f8a922c81feee644a4052d`）。

实现步骤上有两条经验值得记录：

1. **先测再改**。本方案共实测否定了二十余个方向，包括双缓冲、`num_stages` 自动流水、576 宽融合 GEMM、PV 的 LDS bank conflict、QK 累加器拆分、`maca_async_copy`、block_n=16、2 CTA/SM、fp8 等。其中四个方向如果只凭理论会得到相反结论。
2. **数值门不可省**。把 K_pe 拷贝挪进 `ws(0)` 藏在 MMA 后面，理论上很漂亮，实测在 8192 上产生 2.03e-3 的竞态误差；寄存器暂存若用单个临时变量会被 WAR 串行化。这些都不是「变慢」而是「静默出错」。

## 8. 已知边界

以下三档在本硬件上被证明不可达，均已实测而非推断：

- **2048 升到 98**：需要 `k ≤ 0.00855`，即 8.55 微秒。空 kernel 的启动税就是 2.87 微秒，split-KV 的 partial 往返（写 1.23 微秒 + 归并 2.67 微秒）再占 3.9 微秒，剩余 1.7 微秒无法装下 2.3 MB 的拷贝与 QK、PV。
- **16384 升到 99**：需要 `k ≤ 0.0303`，实测最优为 0.031。18.9 MB 的必需流量在该尺寸的有效带宽下就要 16.9 微秒，加固定成本已超过门槛。
- **32768 与 65536 封顶在 99**：100 分要求 `k = 0`，不可能。

另外，判题机在 16384 上是**访存受限而非算力受限**。这一点由一个对照实验确认：把 QK 的 K 维跨两个 warp-group 拆分、每 tile 的 MMA 工作量减半，本地快 1.35 微秒，但判题机读数不变；同一个改动在 32768 与 65536 上却如实体现为变慢。因此 16384 的最后 1 微秒只能靠减少字节或提高有效带宽，而两者都已触及上限。
