## 失败实验：2 CTA/SM（bn=16，单 warp）

动机：shared 从 70KB 压到 18.5KB，目标 2 CTA/SM、128 splits。

实现：threads=64；Q/Q_pe 放 fragment；直接写 partial（去掉 O_shared）；
自定义 acc_o 一维 warp 布局；PV 显式 MFMA 改为单 warp × 32 个 N tile；
bn=16、split target 128。单 warp 最小用例与 torch 参考一致（相对误差 3e-4）。

结果（本地 C500）：
- 2048 / split64：34.3µs（2-warp 基线 23.9µs）
- 16384 / split64：294µs（2-warp 基线 117µs，慢 2.5×）
- 16384 / split128：312µs

结论：单 warp 承担完整 QK/PV 串行链，per-CTA 变慢 2.5×；即使 2 CTA/SM
完全生效也只能追回 2×，净亏。共享内存受限下的 occupancy 路线在此 kernel
形状下不成立。保留作负结果记录：v100_bn16.py（展开 macro）、v101_bn16_dyn.py。

## 已否定：80 splits 假说（167175）

104 splits 在 OJ 上慢 1.35×，104/1.35 ≈ 77，暗示评测机有效并行度可能是 80 个
CTA 而非 64。若成立，64 splits 只用了 80% 的卡，80 splits 可免费拿约 20%。
v102_split80.py 已提交（2048 仍 64；4096+ 用 80），等待结果。

OJ 结果 167175：display **95.67**，逐 case 全面退化
（4096 0.039、8192 0.068、16384 0.109、32768 0.190、65536 0.362）。
结论：评测机有效并行度就是 **64 CTA**；64 splits 恰好一波，任何 >64 的 split
都会进入第二波。split 维度到此封死。

## 软件栅栏融合 merge（v112，已提交 167187）

- 用 atomic_add(return_prev) + while 自旋替代 sync_grid；64 CTA 全部驻留（已由
  split 实验确认评测机 64 SM），栅栏本身仅 0.7µs。
- 心内 merge：每 block 负责 (head, 128 列 tile)；LSE 用 fragment 归约并行算权重
  （串行版本实测慢 11µs，并行后 merge 共 3.7µs）。
- 本地：2048 21.5µs（基线 23.9）、4096 37.1、16384 115.2、65536 404.6；
  正确性 max_abs 与基线一致（1.2e-4 / 6e-5）。
- 预期 OJ：省掉第二次 launch，2048/4096/16384 各跨整数分阈值。

## 根因结论：纯访存延迟受限

逐组件去掉证明计算不是瓶颈（本地 ctx2048，基线 23.9µs）：
- 去掉 PV：20.6（-3.3）
- 去掉 QK：22.7（-1.2）
- 去掉 exp2：24.1（0）
- 去掉缩放：24.4（0）
- 去掉两次归约：23.7（0）
- 去掉归一化除法：23.9（0）

生成代码确认 Q/Q_pe/KV/K_pe 四次拷贝之间无同步、完全重叠。设备拷贝带宽
~939 GB/s，而 kernel 长上下文读带宽仅 ~305 GB/s（约 1/3 峰值）；短上下文
更低（延迟受限）。提升只能靠更高的访存并行度（双缓冲/occupancy），但：

- KV 双缓冲需 64KB，加 K_pe 4KB + S 1KB（即使 Q/O/Q_pe 全放寄存器）
  仍超 64KB 上限 5KB；
- 降 block_n 到 16 需单 warp，per-CTA 慢 2.5×（已实测否决）。

因此在该 kernel 结构下 96.83 已接近硬件上限。

## 硬件上限（最终确认）

torch 设备属性（C500）：
- shared_memory_per_block = 65536，**optin 也是 65536**（无更大动态共享内存）
- shared_memory_per_multiprocessor = 65536 → 每个 SM 只能容纳 1 个 64KB 的 CTA
- regs_per_multiprocessor = 131072（寄存器充足，瓶颈只在 shared）
- warp_size = 64

结论：KV 双缓冲（64KB）加上 K_pe/S 必然超限，2 CTA/SM 需 ≤32KB 也不可能。
在该 kernel 结构下 96.83 已是硬件可达上限；v114（栅栏融合+预取）为技术最优，
OJ display 仍 96.83，内部 ratio 97.0745（略高于 97.0710）。

## Warp specialization 尝试（未成功，记录负结果）

动机：纯带宽基准确认 2 warps 拷贝 831 GB/s、4 warps 1895 GB/s。若让多出的
warp group 只搬数据、group0 只算（2-warp GEMM），理论上每 tile 的 load 从
2.8µs 降到 1.2µs，可省 ~20%。

已验证可用的部分：
- `T.ws(i)` + 256 线程结构可编译运行；单组（只 ws(0)）多 tile 结果正确。
- 无 WS 的“两 buffer 列切分”分解（QK 拆两个 K=256、PV 拆两个 N=256）正确。

失败点：
- 列切分 T.copy 在 loop_range>1 时生成错误地址（group1 源地址出现 -1792 常量），
  1 tile 正确、多 tile 错误。
- 两 group 交替搬运 + 循环（任意同步组合、Pipelined/serial/stage1）在 k>0 时结果错误；
  同样的模式在独立 probe 中正确，说明是 TileLang 0.1.9 race 分支的 ws lowering
  与该 kernel 组合下的缺陷。
- 拷贝放在 ws 外（256 线程）时布局推断按 256 线程生成，与 ws(0) 内 2-warp GEMM
  的 expected layout 不一致，1 tile 即错误。

结论：当前工具链版本下无法可靠实现 4-warp 搬运 + 2-warp 计算。相关文件：
v140-v150（workbench）。潜在收益约 20%，但被编译器缺陷阻断。

### WS 补充实验（v152-v154，全部失败于 loop_range>1）

- v152：256 线程 + ws 分组内逐元素写共享列半区；1 tile 正确，2 tiles 错误。
- v153：同 v152 但 128 线程、无 ws；**多 tile 正确**（但无速度收益，拷贝仅 2 warps）。
- v154：256 线程 + 逐元素拷贝放在 ws 外、仅 compute 在 ws(0)；1 tile 正确，多 tile 错误。
- 用 TileLang 0.1.10（OJ 同版本）复跑 v141 仍错误，排除版本差异。

结论：TileLang 0.1.9/0.1.10 的 ws lowering 在本 kernel 形状下，只要
“循环 + 跨 group 共享 buffer + 多迭代”同时出现就产生确定性错误；所有
可想到的同步/拷贝写法都无法绕过。4-warp 搬运（理论 ~20% 收益）在当前
工具链下不可实现。

### WS 根因（最终定位）

把循环完全静态展开（k 为 Python 常量、两份独立 body）后**仍然错误**，
排除“动态 k / 循环”因素。检查生成代码发现：

- 正确版本（128 线程）：output_partial store 索引为 `i*65536 + (tx>>6)*32768 + ...`（128 线程布局）。
- WS 版本（256 线程）：store 索引为 `(tx&15)*32768 + (tx>>6)*256 + ...`（按 256 线程/复制布局推断）。

即：compute 在 ws(0) 的 128 线程内执行，但 fragment 布局按整个 256 线程 block
推断（replicated），导致一半 fragment 元素从未被计算/写出。单 tile 时编译器
恰好特化正确，多 tile 时不成立。

显式 annotate_layout 会与 gemm 自带的 C 布局注解冲突（ValueError），无法从源码层覆盖。
该缺陷在 TileLang 0.1.9 与 0.1.10 均复现，而 OJ 使用其自带 0.1.10 编译，
因此“本地修编译器”无法嵌入提交。

结论：4-warp 搬运这条路在当前工具链下彻底封死，需要上游修复 ws 的 per-group
layout inference。

### 手写 MMA 内核（v170-v174）：可行但性能不达标

为了绕开 T.gemm 按 block 线程数划分 warp（256 线程必然 4 warp）以及 T.ws
布局缺陷，完全手写了整条计算链：
- QK/QK_pe：T.tvm_mfma，2 warp ×16 列，K=576 分 36 步；
- softmax：共享内存 8 路部分归约（PMAX/PS）+ 128 线程共享原子自旋屏障；
- PV：16 个 n 块静态展开，acc_o[64] 全常量索引（确认在寄存器）；
- epilogue：手写列映射存储；KV/Q 拷贝用全部 256 线程（T.copy）。

结果：**数值全部正确**（max_abs 1.2e-4），证明 4-warp 搬运 + 2-warp 计算
的结构端到端可行。但性能：2048 41.4µs、4096 57.1µs、16384 139.9µs，
比 T.gemm 版本（23.9 / 35.2 / 117）慢 1.2–1.8×。去掉屏障、PV、甚至把线程
数降到 128 都不改变——**手写 TIR 的 MMA 调度质量不及 TileLang 的 gemm 代码生成**。

结论：在 OJ 自带工具链下，4-warp 搬运的收益（约 20%）被人手代码的损失
（约 70%）吞掉。该方向需要上游修复 ws 的 per-group layout inference 才有意义。

## 2026-11-11 深夜：载入路径攻坚（全部负结果）

基线：v219/v031 = OJ 97.17（0.018/0.023/0.035/0.059/0.104/0.195 ms）。

**诊断（关键）**：把 ctx=16384 的 KV tile 拷贝从 512 列减半到 256 列，本地耗时
108.4us -> 54.2us，**严格线性**。说明该 kernel 在长上下文完全受「KV 字节载入吞吐」
支配，计算被完全隐藏。同时 64 CTA / 2 wavefront 的纯拷贝微基准可达 831 GB/s
（13 GB/s per CTA），而 kernel 内只有 ~2.7 GB/s per CTA —— 有 4-5x 的理论空间。

已试并否决（本地 C500，2048 与 16384）：

| 变体 | 机制 | 结果 |
| --- | --- | --- |
| v230 通用融合 merge（split 16/32/64 @2048） | 减少 partial 与 Q 流量 | 45.3 / 29.9 / 19.2us，split<64 严重变慢 |
| v231 merge 8 累加器（免 local 溢出） | merge 寄存器化 | 19.32us（+0.7，否决） |
| p_baronly | 只保留软件栅栏 | 16.41us ⇒ 栅栏占 ~2.2us、merge 仅 ~0.5us |
| v232 atomic_load 轮询 | 降低栅栏原子争用 | 该 op 在 MACA 无 lowering（Unresolved） |
| v250 寄存器预取下一 tile | 用 fragment 预取 256/384 列 | 131.1us @16384（比基线慢 21%） |
| v241/242 LDGSTG(+predicated) pass | 换 ldg/stg 指令 | 108.8 / 108.1us（中性） |
| v260 T.Parallel(prefer_async) | cp.async 注入 | 108.4us（中性，未生效或无效） |
| w1/v190 swizzle / 手写 256 线程 | 4 wavefront 拷贝 + 手写 MMA | 132.6 -> 198.2us @16384（更慢） |
| w2 256 线程 + 融合 merge | 同上 | 191.8us，且数值错误（merge 映射 bug） |

结论：TileLang 的 T.gemm 按 block 线程数推导 warp 划分，M=16/N=32 在 256 线程下
必然得到 2x2（8 行/warp）的非法划分；T.ws 只生成 if(tx<128) 谓词、不改变
layout inference 看到的 thread_bounds，所以「4 wavefront 拷贝 + 编译器级 GEMM」
无法共存。手写 MMA 路径（v173/v190/w1/w2）计算开销远超载入收益。

## 2026-11-12 01:10 — 突破 97.17 → 97.33（新最好成绩）

### 根因：MACA 的 partial barrier 是空函数
`src/tl_templates/maca/common.h:320`
```cpp
template <int barrier_id = 0, int thread_count = 0>
TL_DEVICE void __sync_thread_partial() {
  // INFO: all threads will sync in a warp in maca, does not need partial version
}
```
函数体为空 ⇒ **`T.ws()` 内部的 `T.sync_threads()` 全部是 no-op**。ws 区域跨 2 个 warp
（128 线程 = 2×64）时区域内无法同步。这解释了历史上所有 ws 尝试的失败与本次首次
launch 偶发 NaN（thread 0 自旋时其余 127 线程无人等待即读 partial；首次 launch 的
shared 含垃圾 → NaN，之后是上一轮的有效数据 → 只是小误差，故难以发现）。
可行写法：ws 内不同步，所需同步全部放到 ws 外面的整块 `__syncthreads()`。

### 固定开销最终分解（2048，设备时间）
launch 2.87 + `T.copy(acc_o,O_shared)` **1.62** + partial 写 0.63 + 自旋 0.51 + merge 读 0.70 + Q 0.38 + fill 0.11 + 其余 ~1.3 = **8.12**

### 四视角并行分析（独立 agent，结论与我的独立测量一致）
1. **MMA 流**：QK 20.4ns/MMA、PV 20.6ns/MMA，两种完全相反的依赖结构得到同一个每指令时间
   ⇒ 这是 **MFMA 发射端口地板**，不是延迟；解释了过去"双链/4-warp QK/8-warp PV 全部中性"。
2. **空闲 SM**：32-key 原子使 2048 只有 64 个 tile、4096 只有 128 个；任何加 CTA 的路线都要么
   复制 KV 读、要么跨 104 涨一整波。无解。
3. **算法**：只有行和能免费（已做）；**merge 的全局往返无法消除**。
4. **固定开销**：epilogue 整体 3.1µs，逐项攻击均失败（见上表）。

### 三条硬约束（必须打破其一才可能 587）
1. **shared ≥ 65KB**：双缓冲需要 2×32KB=65536 且 S 还要 1KB ⇒ **差 1KB，算术上不可能**
   （512 维的 tile 2 份已占满 64KB）。少 1KB 的方案都要切片的 `T.gemm` 操作数，而那是 illegal memory access。
2. **fp16 MMA 大于 16x16x16**：无（/opt/maca/include 枚举）。
3. **fragment→shared 的 1.62µs 排空**：四种攻法（padding/转置/thread-major/直连全局）全部更慢。

### fp8 路线的证伪（最后一条能同时解决"1KB 缺口 + MMA 条数"的方向）
动机：fp8 把 KV tile 从 32KB 减到 16KB ⇒ 双缓冲只要 32KB + S 1KB + K_pe 2KB，64KB 轻松装下；
且 fp8 的 MMA 是 16x16x32 ⇒ QK 的 72 条降到 36 条（1.47µs → ~0.74µs）。
理论上 4096 可到 8.06+2×2.3=12.7µs（judge ~14 → 98），2048 可到 10.4µs（judge 11 → 97），即 587。
**但精度先死**：PyTorch 模拟 Q/K 走 e4m3 后，rel_err = 3.8e-2 / 4.4e-2 / 4.1e-2
（2048/4096/16384）——e4m3 只有 3 位尾数，随机数据上就是 4% 量级，远超检查器容差。
Q_pe/K_pe 也转 fp8 几乎不改变这个数（3.7e-2），说明误差来自主干而非 pe 项。
⇒ 未写一行 kernel 代码即否决。

### 指令级终验（三条约束全部落到硬件事实）
1. **shared**：`shared_memory_per_multiprocessor = 65536`（SM 总量，不是每 block）。
   实测 32KB 可起、72KB `mcErrorInvalidValue`。双缓冲 2×32KB + S 1KB = 66560 > 65536。
2. **fp16 MMA**：`/opt/maca/include/cute/arch/mma_sm80.hpp:174` 里
   `MACA_16x16x32_F32F16F16F32::fma` 的实现是**两次 `__builtin_mxc_mma_16x16x16f16`**，
   即"16x16x32"是模拟，**不存在更宽的 fp16 指令**。真正的 16x16x32 只有 i8/f8，
   而 f8 精度实测 4%（不可用）。fp16 累加器也不存在（traits 只有 F32F16F16F32）。
3. **conversion**：acc_o 必须是 fp32（MMA 只出 fp32）⇒ 每次 launch 必须做
   8192 个 fp32→fp16 转换（32/线程），实测 1.5µs，且与 ctx 无关。

⇒ 587 需要的 −3.8µs（4096）恰等于 KV 拷贝成本，而拷贝遮挡同时被 1 和 2 封死。
   585（97.5）是该算法在这台 C500 上的上限；本轮已把每档 ratio 推到 96.77/97.65/98.13/98.43/98.61/98.69。

### fp8 全链路定量（最后一条路，彻底关闭）
关键点：PV 的 A 操作数 S 是 fp16，若 KV 走 fp8 就没有混合精度 MMA —— 也就是说
**只把 QK 换 fp8 根本省不下 shared（PV 仍需 32KB fp16 KV），双缓冲的收益不存在**。
要省 shared 必须 PV 也 fp8，于是精度变成全链路问题。模拟（e4m3，per-tensor 缩放）：

| ctx | QK fp8 + PV fp16 | QK fp8 + PV fp8 |
|---|---|---|
| 2048 | maxrel 4.63e-2 | 4.60e-2 |
| 4096 | 3.24e-2 | 3.83e-2 |
| 16384 | 3.42e-2 | 3.43e-2 |

且 per-element 相对误差（对 >1%max 的元素）超过 100%。任何合理的检查器（rtol 1e-2 量级）
都不可能接受。⇒ **fp8 路线在精度上彻底不可行，不是"没试过"**。

### 终点
到此为止，能拿回 4096 那 3.8µs 的全部手段都已被硬件事实封闭：
更宽 fp16 MMA（不存在，16x16x32 是两次 16x16x16 模拟）、fp16 累加器（不存在）、
fp8（3~4.6% 误差）、更多 shared（SM 只有 64KB，双缓冲差 1KB）、
更多 CTA（每 tile 变慢 76%）、异步拷贝（判题机数值错误）、
fragment→shared 排空（转换吞吐，4 种攻法全败）。
**585（97.5，mean_ratio 97.863）是这台 C500 上该算法的上限。**

## 2026-11-13 **突破**：split 边界按 32-key tile 对齐（submission 168534，97.67 / 586，mean_ratio 97.920）

### 根因
`kv_start = (seqlen_kv * bz) // num_split` 让每个 CTA 的起点落在任意 key 上，
在 104 split 时使并发拷贝效率掉一倍（每 tile 5.74µs vs 64 split 的 1.70µs）。
之前因此判定「split>64 每 tile 慢 76%」，并把 split 数的完整扫描（64/72/80/88/96/104/112）
都读成了「64 最优」——**那个结论是被未对齐污染了的**。

### 修复
```python
tiles_total = seqlen_kv // block_n
kv_start = ((tiles_total * bz) // num_split) * block_n
kv_end   = ((tiles_total * (bz + 1)) // num_split) * block_n
```
配合 `_SPLIT_TARGET_LONG = 104`（正好铺满 104 个 SM）与「>64 split 的融合归并」
（`fuse_lse` 补到 128、`bz < heads*fuse_tiles` 守卫、`fuse_nhalf=(n+1)//2`）。
数值：全 ctx err ≤ 1.2e-4。

### 两条可复用的教训
1. **split 边界必须按 block_n 对齐**（`((tiles*bz)//n)*block_n`）。未对齐会让并发流的
   起点落在任意地址，拷贝效率掉一半，并会**误导 split 数的扫描结论**——我曾因此得出
   「64 最优」，对齐后 104 才是最优（65536：98.69% → 99.07%）。
2. **并发 CTA 越多，带宽越高**：纯流式拷贝 64 CTA = 1114 GB/s，104 CTA = 1565 GB/s。
   这是「铺满 SM 数」在大 ctx 上额外收益的来源。
