# DeepSeek MLA Decode 内核优化报告

本文记录在 MetaX C500 上把 XPUOJ DeepSeek MLA Decode 内核从榜单第 3 名推到第 1 名的完整过程。内容包括判题机的计分规则与硬件上限、性能模型的建立方法、实际采用的二十项优化手段，以及被测量否定的方向。最终成绩为 589/6（display 98.17），领先第二名 0.34。

## 一、问题与规则

### 1.1 计分公式

判题机对每个 case 报告一个内核耗时 `k`（单位毫秒，保留三位小数，即微秒级量化），再按基线耗时 `base` 折算比例：

```
ratio   = base / (base + k)
display = floor(100 * ratio)
```

总分是 6 个 case 的 `display` 整数平均值，因此每提升一个 case 的一档，总分增加 1/6。

| case | base / ms | 起点 k | 起点 display | 终点 k | 终点 display |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2048 | 0.419 | 0.017 | 96 | 0.012 | 97 |
| 4096 | 0.789 | 0.021 | 97 | 0.016 | 98 |
| 8192 | 1.526 | 0.031 | 98 | 0.023 | 98 |
| 16384 | 3.0 | 0.051 | 98 | 0.031 | 98 |
| 32768 | 5.958 | 0.091 | 98 | 0.050 | 99 |
| 65536 | 11.84 | 0.170 | 98 | 0.087 | 99 |

因为 `k` 先量化再参与计算，相邻两档之间往往只差 1 微秒。2048 的 96 档需 `k ≤ 0.01296`，而 `k = 0.013` 给出 96.99%，`k = 0.012` 给出 97.22%——差 0.01 个百分点。

### 1.2 硬件事实

所有结论都在实测基础上得出，不是手册值。

- GPU 为 MetaX C500，104 个 SM，每 SM 共享内存上限 65536 B
- 每个 SM 只驻留 1 个 CTA：grid 从 104 加到 208 时耗时变为 1.78 倍，且与共享内存用量无关
- warp 宽度是 64，不是 32
- 显存带宽强依赖传输规模：4 MB 只有 209 GB/s，8 MB 为 358，64 MB 为 1059，256 MB 为 1373
- 空 kernel 的设备时间是 2.87 微秒，这是无法消除的启动税
- 单条 `16x16x16` fp16 MMA 的吞吐下限约 20.4 纳秒

## 二、性能模型的建立

优化不能靠猜。本节的三种测量方法决定了后面每一步该往哪里下手。

### 2.1 设备时间与复本对照

`torch.profiler` 的 `self_device_time_total` 给出 GPU 侧时间，但直接删掉一段代码会触发死代码消除，测出来的"节省"是假的。可靠做法是**复本对照**：把同一段操作复制一份，测量边际成本。

用这个方法得到的关键结论是：除拷贝外，所有环节都是依赖链延迟，删掉省的是链长，复制一份几乎不花钱。

### 2.2 CUDA Graph Replay

2048 的内核只有 12 微秒，而经 tilelang FFI 的每次调用本身要 8.4 到 9.0 微秒。此时用事件包住 300 次连发测出来的只是主机耗时，不同内核会读出完全相同的数。

改用 CUDA Graph 把 50 次启动压成一次重放，才得到真实值：2048 的 GPU 时间是 12.77 微秒，而不是墙钟的 14.4。

### 2.3 交错 A/B 与轮换顺序

不同进程之间漂移可达 0.7 微秒，且固定顺序会让先跑的模块系统性偏慢约 0.4 微秒。所有对比都在同一进程内交错进行，并按轮换顺序取中位数。

### 2.4 数值门

每个候选在上榜前都要过两道门：与基线在相同输入上比较 `max|v - b|`，并显式检查 `torch.isnan`。NaN 能轻松通过任何"最大值小于阈值"的判断，必须单独查。

## 三、优化手段

按作用层次分成五组。每一项都注明它解决了什么问题、以及为什么有效。

### 3.1 并行度与切分

**split-KV 与 CTA 数选择**。把 KV 序列切成 `num_split` 段，每段由一个 CTA 独立计算部分 softmax 与部分输出，最后归并。C500 有 104 个 SM，且每 SM 只驻留一个 CTA，所以 104 是最优切分数。超过 104 会出现第二波，反而更慢。

**split 边界按 `block_n` 对齐**。这是全场收益最大的单项改动。最初用 `kv_start = seqlen_kv * bz // num_split`，每个 CTA 的起点落在任意 key 上，104 条并发流的分段访问把拷贝效率拖掉一半。改为先算 tile 下标再乘回 `block_n`：

```python
tiles_total = seqlen_kv // block_n
kv_start = ((tiles_total * bz) // num_split) * block_n
kv_end   = ((tiles_total * (bz + 1)) // num_split) * block_n
```

改完后 104 split 反而全面优于 64 split。此前"split 超过 64 会掉档"的结论，是被未对齐的边界污染的。

**按形状分派**。三种内核按 `num_split` 与 `seqlen_kv` 选择：`main_no_split` 用于单段，`main_split` 用于常规分段，`main_split_pref` 用于 4096 及以上的快速路径。这样短上下文不必为长上下文的复杂度付费。

**融合归并**。传统做法是第二个 kernel 读 partial 归并，代价是一次额外的启动。这里改成软件屏障：每个 CTA 写完 partial 后对一个全局计数器做 `atomic_add`，然后自旋等待所有 CTA 到齐，再由指定的一组 CTA 就地完成归并。整个流程在一个 kernel 内结束。

### 3.2 warp 划分与线程数

**QK 与 PV 使用不同的 warp 布局**。QK 是 `M16 N32`，只能在 `T.ws(0)` 内的 2 个 warp 上以 `1x2` 划分运行；PV 是 `M16 N512`，可以在全部 4 个 warp 上以 `1x4` 划分。把 PV 移出 `T.ws` 用满 4 warp 是早期最大的单项收益。

**注意 `T.ws` 内的同步是空实现**。MACA 把 `tl::__sync_thread_partial` 编成空函数，所以 `T.ws` 内部的 `T.sync_threads()` 完全无效。凡是跨 warp 的握手，屏障必须写成 `T.ws` 外面的整块 `T.sync_threads()`。这一条曾导致过一个静默错误：把 K_pe 拷贝挪进 `T.ws(0)` 后，所需的屏障被降级为空实现，8192 上出现 2.03e-3 的竞态误差，刚好越过门限。

**512 线程**。短上下文（单 tile）与长上下文（4096 及以上）都改用 512 线程，PV 走 8 warp 的 `pv_mfma8_ki` 宏，每 warp 负责 64 列。2048 上仅此一项就把 `O_shared` 的 fp32 到 fp16 转储从 2.6 微秒压到 0.81，寄存器反而从 78 降到 48。1024 线程是灾难：32 个 warp 把每线程寄存器压到 64 个，直接溢出。

**手写 MMA 宏**。PV 不用 `T.gemm`，改用 `T.tvm_mfma` 手写的 `pv_mfma4_ki` 与 `pv_mfma8_ki`，显式控制每个 warp 的列范围与累加器布局。`T.gemm` 走 PV 会慢 1.7 倍。

### 3.3 访存与共享内存

**128 位向量化拷贝**。KV 的全局到共享拷贝由编译器自动生成 128 位向量化加 swizzle，已无优化空间：

```
for (int i = 0; i < 8; ++i)
  *(uint4*)(KV_shared + swizzle(i, tid)) = *(uint4*)(KV + base + i*2048 + tid*8);
```

**修复 `O_shared` 的 16 路 bank 冲突**。行跨度是 512 个 half，即 256 个 word，对 32 取模正好为 0，于是持有第 0 到 15 行同一列组的 16 条 lane 全部命中同一个 bank。这是 16 路冲突，代价 2.74 微秒，而此前被误记为"0.81 微秒的转储开销"。

修复方式是把行跨度补到 520 个 half（260 个 word，对 32 取模为 4，降到 2 路），同时保持 1040 B 的行宽仍是 16 B 对齐，全局 store 不会退化成 8 字节：

```python
O_shared = T.alloc_shared([valid_block_h, dim + 8], dtype)
T.copy(acc_o, O_shared[0:valid_block_h, 0:dim])
```

**修复 `S_shared` 的 8 路冲突**。用旋转索引 `(sj + si*4) % 32` 把每行错开 4 个 half，冲突消除。

**寄存器暂存 32 键预取**。这是从 586 走到 587 的关键。原先每个 tile 的循环头部要同步地把 32 键 KV 从全局搬到共享，这段延迟完全暴露。改成把整块 32 键暂存进寄存器：LDG 在循环头部发出，STS 在 PV 算完、当前 tile 的共享数据已死后才落回。它正好落在已有屏障之内，不新增屏障，也不多占共享内存。

三个坑必须避开：

- 寄存器上限是 254，且只通过 `*(uint4*)` 强转访问的局部数组会被降级到栈上（148 B 栈帧导致 101 微秒）。要强转写、逐元素读。
- TileLang 会给各分块复用同一个临时变量，导致所有 LDG 被 WAR 串行化。必须用 `kv_s0` 到 `kv_s7` 这样的独立缓冲，让每条 LDG 有独立的目的寄存器。
- `T.sync_threads()` 会强制未完成的 LDG 先完成，所以预取的掩护范围只有"发出点到下一个屏障"之间的代码，不是整个迭代。

**预取拆两组跨屏障区间**。把 36 KB 的下一块预取拆成两组，分别放在两个屏障区间内发出，同时把 PV 的两半改成连续，消掉编译器保守插入的 WAR 屏障。每 tile 的屏障从 5 个降到 3 个。

**K_pe 拷贝重排**。K_pe 只有 4 KB，但它的 DRAM 延迟同样在关键路径上。把它排到 KV 拷贝之前发出，让 L2 命中的 Q 加载掩护它。

### 3.4 计算链

**合并 QK 的两个 GEMM 无意义**。把 K=512 与 K=64 两个 GEMM 合成一个 K=576 的 GEMM 是常见的直觉，但实测收益 ±0.1 微秒。原因是 MACA 本来就把 32 条加 4 条 MMA 发成同一个累加器上的连续序列，中间既没有屏障也没有回写，融合只换来一个 1152 B 的非二次幂行宽去扰动 swizzle。

**QK 的 K 维跨 warp-group 拆分**。QK 原本是 32 条串行依赖的 MMA，只跑在 128 线程上，512 线程里另外 384 条空转。把 K 维切成两半，`T.ws(0)` 算 K 属于 [0,256)，`T.ws(1)` 算 [256,512)，两组各 16 步并行，最后经共享内存相加。两组各 18 步，每 tile 的 QK 从 0.51 微秒降到 0.26。

**warp 级 LSE 归约**。归并阶段的 LSE 分母原本用 `T.reduce_sum`，在 MACA 上会展开成带无保护偏移 64 的共享内存往返，而结果只有 0 号线程用。改成 5 次 `T.warp_reduce_sum`，0.93 微秒降到 0.12。

### 3.5 固定开销

短上下文没有循环可摊，固定开销就是全部。逐项计价后的处理：

**去掉 prologue 屏障**。Q 与 KV 的加载互不依赖，原本中间有一道屏障，删掉后两次加载能同批发出。

**尾部屏障裁剪**。最后一次循环迭代不需要那道保护"下一 tile 复用缓冲"的屏障，用 `if k + 1 < loop_range_split` 把它折掉。

**到达自旋改 volatile load**。原实现用 `atomic_add(State, 0)` 轮询，64 或 104 个 CTA 争抢同一个计数器的 RMW。MACA 的 `T.atomic_load` 是一条普通 volatile load，语义相同但不再有 RMW 争用，同时消掉了掉队尾巴。另外只让真正参与归并的 64 个 CTA 去轮询，其余 40 个不再捶同一行缓存。

**按 shape 分配到达计数器**。归并屏障的返程目标写作 `(fuse_old // num_split + 1) * num_split`，这要求计数器每次启动都从 `num_split` 的整数倍开始。如果同一进程先后跑 64 split 和 104 split，就会永久自旋——基线里确实存在这个死锁。改成每个 shape 各存一个计数器，零成本且彻底消除。

**短上下文走单 tile**。2048 分配 64 split，每个 CTA 恰好一个 tile。实测每个额外 tile 值 6.5 微秒，所以减少 split 必然更差，64 是唯一正确的取值。

## 五、被否定方向

这些方向都实测过，记录在此以免重复投入。

**共享内存双缓冲**。需要 2×32 KB，加上 16 KB 的 Q 已经超出 64 KB。`O_shared` 已被分配器与 `KV_shared` 完全别名，删掉它腾不出空间。

**把 Q 放进寄存器**。确实可行，共享内存从 56576 B 降到 40192 B，但 MMA 的 A 操作数要在两个 wave64 上复制，寄存器变成每线程 128 个 half，而基线已用掉 228 个。固定代价 +5.4 微秒，超过腾出空间的收益。

**block_n = 16**。会让 QK 失去一半 wave 并行，实测慢 59%；且 TileLang 在 N=16 时 `warp_cols` 为 0，直接除零崩溃。

**`maca_async_copy`**。本地数值正确，判题机全部 WrongAnswer。

**`num_stages` 流水线**。=1 时每 tile 屏障从 3 个变 5 个，慢 2.5 微秒；=2 需要 93440 B 共享内存，无法启动。

**K=576 融合 GEMM**。见 3.4，收益 ±0.1 微秒。

**消除 partial 往返**。partial 数组在 2048 是 1 MB，写读各一次。减少 split 会让每个 CTA 多跑一个 tile（6.5 微秒），得不偿失。

**合并读向量化**。合并读是带宽受限而非指令受限，整块删掉只省 1.46 微秒，向量化反而增加归约级数。

**`pv_b` 的 LDS bank 冲突**。确实是 2 路冲突，把它完全消掉（wavefront 从 96 降到 48）后时间一点没变——PV 的 LDS 不在关键路径上，16 个 warp 分摊到 4 个调度器足以掩盖。

**workspace 缓存**。`T.alloc_global` 不是 torch 张量，而是降级成 host wrapper 里的池化设备 workspace，Python 侧没有 `torch.empty`。而且 2048 时主机路径只要 9.0 微秒、GPU 要 16.6 微秒，主机侧永远动不了分数。

**cache hint**。TileLang 的 `eviction_policy` 在 MACA 后端只对 TMA 路径生效，本项目走 SIMT；`annotate_l2_hit_ratio` 在 MACA 后端根本没有引用。

## 六、本地收益为何不迁移

开发机是 50% 带宽切片，判题机不是。这一条解释了本次会话中反复出现的现象：本地测出 −1 到 −2 微秒的改动，判题机上纹丝不动。

最能说明问题的是 QK 的 K 维拆分。它把每 tile 的 MMA 工作量减半，本地 16384 快 1.35 微秒，但判题机 16384 完全不变，同一个改动在 32768 和 65536 上却实打实地变慢（0.050 到 0.052、0.087 到 0.090）。

这说明判题机对计算类改动是敏感的，只是在 16384 这个规模上**访存才是瓶颈**：18.9 MB 数据在 31 微秒内搬完，有效带宽约 610 GB/s。因此在该 case 上，任何纯计算优化都不会体现。

## 七、剩余空间

16384 目前 0.031，距离 99 档的 0.030 只差 1 微秒，但四次方向完全不同的实质改进都没能把它推下去。要突破只能在减少搬运字节或提高有效带宽上下手，而两者都已接近上限：tile 阶段的拷贝已跑到可达峰值的 89%。

其余 case 的缺口更大且更硬。2048 要 8.55 微秒，而空 kernel 的启动税就是 2.87 微秒；4096 要 7.97 微秒（现 16），8192 要 15.4（现 23）。32768 与 65536 已经是 99，100 档在数学上不可能达到。
