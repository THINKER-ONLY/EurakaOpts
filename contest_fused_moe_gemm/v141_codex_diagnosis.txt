FAMILY_RANKING

1. **E16 up-FC1 feature streaming, FC2 unchanged**  
   Keep standard high-level GEMM for `gate_output`; compute only `up_output` in feature chunks; apply chunked SwiGLU into `gate_output`; then run v136 FC2 unchanged. Best candidate: materially different memory-lifetime change, no custom dense FC1, no retained memory increase.

2. **FC1+FC2 feature streaming with partial FC2 accumulation**  
   Compute activation chunks and immediately GEMM them into partial FC2 outputs. Larger memory upside, but needs accumulation across K chunks, likely fp32/ordering-sensitive, and would require custom add/reduction semantics. Too risky.

3. **Shape-specific standard GEMM expert sub-batching**  
   Split FC1 by expert groups while keeping high-level BMM. This overlaps with v116/v122-style chunking and adds launches without clear memory or compute reduction. Low novelty and low expected gain.

DUPLICATE_AUDIT

Selected candidate is not v140 custom dense FC1+SwiGLU. It keeps `@`/standard high-level GEMM-backed FC1.

It is also not:
- plain FC2 expert chunk enumeration,
- elementwise wider block probing,
- combined `[gate; up]` retained weight,
- dynamic M176/M160,
- preallocated `torch.bmm(..., out=...)`,
- external prepare/cache trick,
- local transpose hoist.

Dataflow:

gate_output = packed_input @ gate_w.transpose(1, 2)

for feature chunk f0:f1, size 2048:
    up_chunk = packed_input @ up_w[:, f0:f1, :].transpose(1, 2)
    swiglu_feature_chunk(gate_output, up_chunk, group_offsets, gate_output)

activation = gate_output

```

For E32/E64, leave v136 exactly unchanged.

NUMBERED_MODIFICATION_POINTS

1. Copy v136 to `v141_e16_stream_up_fc1_chunks.py`.
2. Add `_swiglu_feature_chunk_kernel(intermediate, feature_start, feature_chunk, num_experts, expert_block_m)`.
3. Kernel reads full `gate_output[..., feature_start + local_j]`, reads `up_chunk[..., local_j]`, writes activation back into `gate_output[..., feature_start + local_j]`.
4. Add tuple of four chunk kernels for E16 case1: starts `0, 2048, 4096, 6144`.
5. In `run_kernel`, branch only for `num_experts == 16 and hidden == 2048 and intermediate == 8192`.
6. Compute full `gate_output` once using standard `@`.
7. Compute `up_chunk` with standard sliced high-level `@`; do not use `torch.bmm`.
8. Reuse v136 FC2 and unpack exactly.

DATAFLOW_PROOF

SwiGLU is feature-independent:
`activation[e, m, k] = silu(gate[e, m, k]) * up[e, m, k]`.

Splitting `up` by feature columns does not alter dependencies. After all four chunks, `gate_output` contains the full activation tensor with the same shape and indexing v136 passes to FC2.

FC2 sees identical logical input:
`activation @ down_w.transpose(1, 2)`.

MEMORY_LIFETIME_PROOF

v136 case1 peak retains:
- `packed_input`,
- full `gate_output`,
- full `up_output`,
- FC2 temporary.

v141 case1 retains:
- `packed_input`,
- full `gate_output`,
- one `up_chunk`,
- FC2 temporary after up chunks are done.

No cross-case retained memory increase. E32/E64 unchanged. No cached combined weight. Kernel cache grows only by four small compiled kernels, not tensor memory.

EXPECTED_GAIN

Expected gain is shallow: likely `0%` to `1%`, mainly from lower peak allocation pressure and shorter `up_output` lifetime. It may regress if four smaller GEMMs lose more launch/GEMM efficiency than the allocator/memory benefit recovers.

Credible chance exists because case1 has large `intermediate=8192`; chunk size `2048` still leaves a substantial GEMM N dimension.

CORRECTNESS_RISKS

- Sliced high-level matmul must be accepted by sandbox via `@`.
- Feature chunk indexing must cover exactly `[0, 8192)`.
- In-place write to `gate_output` is safe only after the corresponding gate values are read for that feature chunk.
- Padding guard must match v136’s `group_offsets` behavior.

PERFORMANCE_RISKS

- Four up-GEMM launches replace one up-GEMM launch.
- Smaller N may reduce GEMM efficiency.
- Extra SwiGLU launches replace one full SwiGLU launch.
- If allocator pressure is already hidden by runtime caching, timing may regress.

IMPLEMENTATION_INSTRUCTIONS

Use chunk size `2048`. Do not touch E32/E64.

Do not use `torch.bmm`, `out=`, retained combined weights, or custom FC1 accumulation. Keep all FC2 code byte-for-byte equivalent except variable names needed for the branch.
