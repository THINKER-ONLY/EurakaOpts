```text

Add a TileLang metadata kernel that assigns each expert to one of a small number of fixed-M buckets based on `group_size`. Then compact active rows into dense bucket buffers:

```text
bucket0: [B0, M0, I]
bucket1: [B1, M1, I]
...
```

where `M0/M1/...` are fixed capacities, for example:

```text
M_BUCKETS = [16, 32, 64, 128, 192]

Each expert with `0 < group_size <= M` goes into the smallest matching bucket. FC2 runs as bounded batched matmuls per bucket, not per expert.

BATCHED_GEMM_PLAN

Use fixed bucket capacities:

```text
NB = 5
M_BUCKETS = [16, 32, 64, 128, 192]
```

For each bucket capacity `M`, launch at most one batched/grouped FC2 operation:

```python
# Pseudocode only. No .item(), no expert loop.
for bucket_id, M in enumerate(M_BUCKETS):
    # Fixed launch per bucket, not per expert.
    # Batch count is represented by device metadata or fixed E upper bound.
    # Inactive bucket slots have zero rows and are ignored on scatter.
    bucket_act_M = workspace.act[bucket_id]      # [E, M, I] or compacted [max_bucket_E, M, I]
    expert_ids_M = metadata.bucket_expert_ids[bucket_id]

    bucket_out_M = grouped_batched_matmul(
        A=bucket_act_M,                          # [Bmax, M, I]
        B=W2.indexed_by(expert_ids_M),           # [Bmax, I, O]
        active_mask=bucket_row_counts[bucket_id] # device metadata
    )
```

If the available high-level API cannot accept device-indexed weights directly, use a TileLang gather-weight-view/copy kernel into a per-bucket contiguous weight buffer:

```text
bucket_w2: [Bmax, I, O]
```

Then call ordinary batched matmul:

```text
[Bmax, M, I] x [Bmax, I, O] -> [Bmax, M, O]
```

This is still bounded: at most `NB` weight-gather kernels, `NB` compact kernels, `NB` batched GEMMs, and `NB` scatter kernels. No expert-count launch scaling.

OUTPUT_MAPPING_PROOF

For each expert `e`, v141 computes FC2 for rows:

```text
r in [0, group_sizes[e])
act_packed[e, r, :]
```

v143 assigns expert `e` to exactly one bucket `b` where:

```text
M_BUCKETS[b-1] < group_sizes[e] <= M_BUCKETS[b]
```

or the first bucket if `group_sizes[e] <= 16`.

The compact kernel writes:

```text
bucket_act[b, slot(e), r, :] = act_packed[e, r, :]
```

for exactly the same active row domain:

```text
0 <= r < group_sizes[e]
```

The batched FC2 computes:

```text
bucket_out[b, slot(e), r, :] =
    bucket_act[b, slot(e), r, :] @ W2[e]
```

The scatter kernel writes:

```text
final[token_index(e,r), :] = bucket_out[b, slot(e), r, :]
```

using the same group offsets/routing metadata as v141 unpack. Padded rows `r >= group_sizes[e]` are never scattered, so they cannot affect correctness.

Expected gain comes from removing padded FC2 work for experts with small `group_size`.

v141 FC2 effectively pays close to:

```text
E * 192 * I * O
```

v143 pays approximately:

```text
sum_e bucket_ceil(group_sizes[e]) * I * O
```

plus compact/scatter overhead.

Best case: many experts have small groups, saving 25-60% of FC2 arithmetic.  
Worst case: most experts are near 192 rows, savings are small and overhead can regress.

Expected benchmark target: improve worst/median on cases with skewed routing while preserving v141-style behavior on dense cases.

1. Compact plus scatter overhead may dominate when group sizes are dense.

5. Atomic bucket assignment overhead is small but nonzero.
