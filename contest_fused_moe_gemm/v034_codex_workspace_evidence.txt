    d_expert,
    n_routed_experts,
    group_sum,
    padded_group_sum,
    group_count,
    block_token=128,
    block_dhidden=128,
    block_dexpert=128,
    threads=256,
    num_stages=1,
):
    scale = 1.44269504  # log2(e)
    dtype = T.float16

LOCAL_API_EVIDENCE:  
本地证据支持“十参数 `run_kernel` + `prim_func` 内 `T.alloc_global` + 多个顺序 `T.Kernel`”具备语法/编译路径可行性。MLA 候选 [submission.py](</mnt/d/C_data/EurakaOpts/mla_decode/v027_b32_8k_fused_split32/submission.py:59>) 在单个 `prim_func` 内 `T.alloc_global` 分配 `glse/output_partial/score_partial` 等，并顺序执行多个 `T.Kernel`，Python 侧不传 workspace。只能说这是本仓库 TileLang 用法先例，不能虚构为 OJ accepted 事实。官方参考 [custom_fusedmoe.py](</mnt/d/C_data/EurakaOpts/contest_fused_moe_gemm/reference/custom_fusedmoe.py:40>) 也证明“两 kernel + up_logits intermediate”的算法结构，但它是历史 11 参数接口。

V002_REUSE_ALLOWED: NO  
原因：v002 可作为结构参考，不可作为实现复用。它有旧结构遗留风险：`M = ceil(group_sum / 128) + group_count`，没有采用当前 v032/v033 的 `num_blocks_m = group_idx_for_bx.shape[0]`；padding/output 处理不完整；第二 kernel 读写边界需要重审；不能直接提交。

V034_SELECTED: YES  
PARENT: `contest_fused_moe_gemm/v033_serial_fc1_accumulator.py`  
原因：v033 是当前更接近正确数学的父版，已把 gate/up 串行独立计算，C500 repeat35 稳定记录存在；v032 虽保留并行 gate/up locals，但 v033 更适合作为“正确父版”迁移到双 kernel global workspace 结构。v032 可作为对照参考，不应作为主父版。

P1: 保持十参数外部接口  
原因：`run_kernel(stacked_expert_tokens, gate_w, up_w, down_w, routed_expert_weights, group_sizes, group_offsets, group_padded_offsets, group_idx_for_bx, out)` 不新增 `workspace/up_logits` 参数；`out` 是唯一外部 INOUT。

P2: 在 `prim_func` 内 `up_logits = T.alloc_global((padded_group_sum, d_expert), dtype)`  
原因：满足十参数接口，同时复用 TileLang 本地 `alloc_global` 先例。workspace 生命周期由编译后 kernel 管理，不由 Python/torch 分配。

P3: kernel1 只计算 FC1 intermediate  
原因：拆出 gate/up GEMM，避免当前单 kernel FC1+FC2 复合路径的 segfault 主题。kernel1 输出 `SiLU(gate) * up` 到 global `up_logits`。

P4: kernel1 使用独立 FP32 `gate_local` / `up_local`  
原因：必须避免 gate/up 累加混入。每个 expert tile 开始分别 `T.clear(gate_local)`、`T.clear(up_local)`，hidden tile 循环内分别 GEMM 累加。

P5: kernel1 仅有效行写 `up_logits`，padding 中间显式安全  
原因：`i < actual_rows` 才写有效 token。对无效行要么写 0 覆盖完整 tile，要么保证 kernel2 对 `i >= actual_rows` 不读；推荐写 0，降低未初始化 global 被误读风险。

P6: kernel2 按 output tile 对完整 `d_expert` 累加  
原因：kernel2 grid 应为 `(num_blocks_m, ceildiv(d_hidden, block_hidden))`，内部循环 `ceildiv(d_expert, block_expert)`，从 `up_logits` 和 `down_w` 累加到 FP32 `out_local`。

P7: kernel2 应用 route weight 并处理 padding output  
原因：有效行 `out = out_local * routed_expert_weights[raw_start + i]`；无效 padding 行必须写 0，避免旧值污染。

P8: 只读九输入  
原因：`stacked_expert_tokens/gate_w/up_w/down_w/routed_expert_weights/group_sizes/group_offsets/group_padded_offsets/group_idx_for_bx` 均不得写；仅 `out` 写。

P9: 维持当前 shape/key 规则并使用 `num_blocks_m`  
原因：v033 的 `num_blocks_m = group_idx_for_bx.shape[0]` 是当前正式十参数布局的关键，不能退回 v002 的 `M` 估算。

WORKSPACE_SIZE:  
`up_logits` 最大为 `padded_sum * d_expert * 2` bytes。粗略上限按 `padded_sum <= group_sum + 256*n_experts`：case1 `<=6368*8192*2 = 99.5 MiB`，实际大概率 `4096*8192*2 = 64 MiB`；case2 `<=12736*2048*2 = 49.8 MiB`；case3 `<=25472*2048*2 = 99.5 MiB`。量级可接受但不能假设 OJ 内存一定足够，必须实测。

INTERFACE_RULE_COMPLIANCE: PASS_TO_IMPLEMENT  
十参数 Python 接口可保持；不需要 torch workspace；`up_logits` 只在 `prim_func` 内部。

KNOWN_RISKS:  
结构改动较大，虽然主题是“global workspace 双 kernel”，但实现包含多个必要子点。主要风险是 TileLang 内部 global allocation 的 OJ 内存策略、kernel 间可见性、padding 未初始化读、FP32 到 FP16 intermediate 精度变化、以及 v024-v033 单 kernel segfault 根因是否仍会被某个 pattern 触发。

STATIC_GATE_REQUIREMENTS:  
必须逐点静态复验 P1-P9；确认无外部 workspace 参数、无 torch 分配、无旧 v002 `M` 估算、无 gate/up 共用累加、无 padding 读未初始化、无输入写入、无未列语义变更。

SERVER_TEST_REQUIREMENTS:  
先 `py_compile`；再服务器 case1/case2/case3；检查 compile success、runtime、数值误差、readonly inputs；至少对最敏感 case 做重复运行稳定性测试。workspace 内存必须由实际 OJ 结果确认。

OJ_EXPECTATION:  
可以批准进入实现和服务器验证；不能静态声称会过。合理预期是：若 v024-v033 的 segfault 来自单 kernel FC1/FC2 组合或寄存器/生命周期压力，v034 有机会绕开；若来自更底层 GEMM/store/padding 或 TileLang runtime 问题，则仍可能 RuntimeError。

GATE: PASS_TO_IMPLEMENT  
BLOCKERS: 无静态 blocker；提交前 blocker 是必须完成服务器三 case 与重复稳定性验证。
