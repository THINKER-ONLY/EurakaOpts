FAMILY_RANKING

1. Flattened/block-diagonal FC2 via high-level `@`: highest theoretical upside, but blocked. It cannot be expressed correctly without dense zero materialization or an unsupported sparse/grouped view.
2. Combined gate/up FC1 without materialized combined weights: blocked. Standard `@` needs one right-hand tensor; two independent expert weights cannot be fused into one matmul without either materializing `[gate; up]` or doing two matmuls.
3. Case-specific retained/materialized combined or block weights: blocked. v132 already showed variant-correlated OOM risk from large retained combined FC1, and FC2 block weights are much larger.

DUPLICATE_AUDIT

Not repeating retired families: no custom grouped FC2, no custom dense FC1, no host per-expert loop, no static `M<192`, no row split, no slab streaming, no prescale, no metadata/chunk/block/del probe, no explicit `torch.bmm`.

This is also not a v152 retry: it preserves high-level `@` only and does not call `torch.bmm`.

SELECTED_ARCHITECTURE

BLOCKED. No safe v153 architecture meets the requested “materially different with plausible >3% upside” threshold under the current constraints.

NUMBERED_MODIFICATION_POINTS

1. Do not implement flattened FC2.
2. Do not implement block-diagonal FC2.
3. Do not implement combined FC1 without a real weight tensor.
4. Keep v149 as operational parent.

SHAPE_AND_MEMORY_PROOF

For FC2, current math is per expert:

`activation[e]: [192,I] @ down_w[e].T: [I,H] -> [192,H]`

A single flattened dense matmul would need either:

`[E*192, E*I] @ [E*I, E*H] -> [E*192, E*H]`, then select each expert’s `H` slice, or an equivalent dense block structure.

Dense block-diagonal FC2 weight sizes:

- Case2: `[32*2048, 32*7168]` fp16 = about `30 GiB`
- Case3: `[64*2048, 64*7168]` fp16 = about `120 GiB`

Even storing only nonzero blocks would be about the original `down_w` size, but standard dense `@` cannot consume that as a sparse block-diagonal view. `as_strided` cannot express the required zero regions because they are not affine memory strides.

For combined FC1, a safe single `@` needs combined weights:

`packed_input [E,192,H] @ combined_w.transpose(1,2) [E,H,2I]`

Materialized combined weight cost:

- Case1: `16*2*8192*2048*2` = about `1.0 GiB`
- Case2: `32*2*2048*7168*2` = about `1.75 GiB`
- Case3: `64*2*2048*7168*2` = about `3.5 GiB`

v132’s E64 combined-FC1 path correlated with case3 generator OOM, so this memory family is not safe.

OPERATOR_API_PROOF

Allowed:

- Existing high-level `@`
- Existing TileLang pack/SwiGLU/unpack kernels

Blocked or unavailable:

- Explicit `torch.bmm`: v152 TorchProxyError
- Sparse/block-sparse matmul API: not part of accepted path
- Custom grouped GEMM: retired after v151 regression
- Host per-expert matmul loop: retired after v142 regression

EXPECTED_GAIN

No selected candidate has defensible expected gain above 3%.

Flattened FC2 could reduce launch count only if block-diagonal dense matmul were free, but it is not expressible without catastrophic memory and extra cross-expert compute. Combined FC1 showed only partial 1-1.5% gains in v132 and failed full qualification.

CORRECTNESS_RISKS

- Flattened FC2 without true block isolation computes cross-expert products.
- Dense block output requires diagonal expert slice extraction, adding another custom unpack/gather path.
- Combined FC1 can introduce aliasing/lifetime issues already seen in earlier combined-output variants.

PERFORMANCE_RISKS

- Dense block-diagonal FC2 multiplies mostly zeros or materializes huge tensors.
- Expanded activations increase memory traffic by `E`.
- Combined FC1 increases peak memory enough to threaten OJ generation/runtime memory.
- Any custom replacement for backend `@` risks repeating v151’s 2.2x E64 regression.

IMPLEMENTATION_INSTRUCTIONS

Do not create v153 code from these candidates. Record v153 as blocked and keep `v149_swiglu_group_sizes_metadata.py` as the parent. Next viable work needs a genuinely new allowed primitive or a proven way to reduce FC2 materialization without sparse/block-diagonal storage.

BLOCKED: do not submit.
